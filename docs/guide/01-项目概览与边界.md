## 1. 项目定位

**Fitness Coach Agent** 是一个**多运动健康垂直领域**的 AI Coach：用户通过 Web 聊天界面提问，系统以 Multi-Agent 方式编排 **训练（training）**、**营养（nutrition）**、**安全（safety）**、**档案（profile）** 等子能力，结合 **RAG 知识库** 与 **7 个领域工具**，给出可引用、可个性化、带安全护栏的建议。

默认 LLM：**DashScope Qwen**（`qwen-plus` + `text-embedding-v3`）。数据存储：**PostgreSQL 16 + pgvector**。

## 3. 明确边界（不做什么）


| 不做                     | 原因                                  |
| ---------------------- | ----------------------------------- |
| 客服 / handoff / 工单      | 项目定位是 Coach，非客服系统                   |
| Legacy 双轨 Orchestrator | 仅保留 LangGraph 一条路径                  |
| Neo4j 集群               | Graph 存 PostgreSQL 表，MVP 运维简单       |
| HIPAA 级医疗合规            | portfolio 级 disclaimer + guardrails |
| 移动端 / IoT / 穿戴设备       | Web MVP                             |
| 自训 base model          | 默认 API；LoRA 仅本地可选实验                 |

## 4. 与 reference 仓库关系

设计文档提到借鉴 **customer-service-agent** 的：

- SSE 协议分层（`done` 仅 ChatService 发）
- `DashScopeClient` 封装
- RAG / Memory / Observability 服务分层
- RBAC 中间件

**不移植**：handoff、工单、Legacy `AgentOrchestrator`、客服知识库。

## 常见追问

### Q1: 为什么做运动健康而不是通用 ChatBot？

**答**：垂直领域能展示 **RAG + Tool + 安全规则 + 个性化 profile** 的组合价值；通用 Bot 难以体现 Multi-Agent 分工和 benchmark 评测闭环。

**追问**：和 ChatGPT 套壳区别？  
**答**：有显式 **Planning 图**、**并行 sub_agent**、**7 工具 ReAct**、**Hybrid RAG citation**、**agent_run 可观测**；不是单 prompt 直连。

### Q2: 项目最大技术难点 TOP3？

**答**：① ChatService/Orchestrator **职责分离** + SSE `done` 语义；② **并行 sub_agent** 状态 merge + recovery；③ **replace/delta** 流式契约与前端一致。

### Q3: 如果只有 2 周会砍什么？

**答**：Graph RAG、Benchmark 仪表盘、LoRA 实验；保留 LangGraph + Hybrid RAG + 核心 4 工具 + SSE Chat。

### Q4: 生产化还差什么？

**答**：Celery 替代 BackgroundTasks、多 worker SSE sticky、benchmark 持续扩充与 faithfulness 真实 API 抽样、监控告警。见 [reference/COACH_HA.md](../reference/COACH_HA.md)。

### Q5: 如何证明 Agent 比单 LLM 好？

**答**：Benchmark 81 条样本测 faithfulness / tool_use；并行 training+nutrition 场景单 LLM 难稳定拆任务；观测 timeline 可审计每步 tool 调用。
